# ModelMate

[![tests](https://github.com/ohsewool/modelmate/actions/workflows/tests.yml/badge.svg)](https://github.com/ohsewool/modelmate/actions/workflows/tests.yml)

ModelMate는 CSV 데이터를 업로드하면 데이터 구조 분석, 예측 타깃 추천, 모델 비교, 근거 기반 보고서, 예측 API 준비도까지 하나의 흐름으로 제공하는 Korean-first Agentic AutoML SaaS MVP입니다.

English summary: ModelMate turns CSV data into explainable predictions, grounded reports, and reusable APIs through a guided AI analyst workflow.

## What It Does

ModelMate는 비전문가도 CSV 기반 예측 분석 흐름을 이해하고 재사용할 수 있도록 만든 졸업 프로젝트이자 포트폴리오 서비스입니다. 단순히 모델을 학습하는 데서 끝나지 않고, 사용자의 분석 목표를 계획으로 바꾸고, tool call, observation, decision, validation, human review, artifact 기록을 남기는 방향으로 확장했습니다.

## Key Features

- CSV 업로드와 데이터 구조 분석
- schema validation, target recommendation, leakage check
- classification/regression 모델 비교와 AutoML training adapter
- Agent Mode: goal -> plan -> tool call -> observation -> decision -> validation -> artifact
- Agent Run Detail에서 persisted trace 확인
- human review/recovery foundation
- grounded report preview/export
- project/run/report/workspace reuse
- project-scoped prediction API token/readiness
- usage limits, monitoring/error ID, feedback/pilot inquiry foundation
- starter pack/sample dataset demo flow

## Product Workflow

```text
CSV 업로드 또는 샘플 선택
-> 분석 목표 입력
-> Agent Run / Plan 생성
-> 데이터 점검과 타깃 추천
-> leakage 검토
-> AutoML 모델 비교
-> 성능 평가와 XAI 요약
-> validation / human review
-> grounded report
-> prediction API readiness
```

## Agentic AutoML Workflow

ModelMate의 Agent Mode는 현재 tabular CSV predictive analysis에 집중합니다.

- PR-27: goal-first Agent Run과 deterministic plan 저장
- PR-28: tool handler 실행과 trace record 저장
- PR-29: trace/decision UI
- PR-30: human review/recovery
- PR-31: optional planner interface와 deterministic fallback
- PR-32: portfolio/demo/docs polish

Agent Mode는 “완전 자율 데이터 과학자”를 의미하지 않습니다. 지원하지 않는 목표나 위험한 분석은 제한, 경고, human review 또는 unavailable 상태로 정직하게 표시합니다.

## Demo Scenario

1. Landing page에서 ModelMate의 CSV 예측 분석 흐름을 소개합니다.

7. 모델 비교, report, prediction API readiness를 보여줍니다.
8. human review/recovery가 필요한 상황은 경고와 다음 행동으로 설명합니다.

## 30초 데모 — 서버 없이

```bash
python3 scripts/make_demo_data.py
python3 scripts/demo.py --leaky                    # 검사 적용
python3 scripts/demo.py --leaky --ignore-leakage   # 권고를 무시하면
```

프로파일 → 누출 검사 → 학습 → 증거 검증 → 보고서까지 한 파일에 대해 전 과정을 출력한다. 두 번 돌리면 차이가 보인다: 권고를 적용하면 AUC가 1.0에서 0.778로 내려가고 검증은 `grounded`가 되며, 무시하면 검증이 `invalid`로 판정하고 **보고서가 스스로 차단 상태를 밝힌다** — 요약 첫 문장과 한계 고지에 차단 사유가 들어간다.

보고서 작성을 아예 막지는 않는다. 막으면 사용자는 이유를 볼 수 없고, 근거를 보여주는 것이 이 제품의 요지다.

**이 문장은 원래 "검증이 보고서 작성 자체를 막는다"였고, 그런 일은 일어나지 않았다.** 확인해보니 더 나쁜 것이 있었다 — 권고를 **따른** 실행도 똑같이 차단됐다. 증거 묶음에 넘어가는 누출 정보가 학습이 쓴 컬럼이 아니라 원본 데이터셋 전체의 것이었기 때문이다. 학습 뒤 재검사는 `low`/`high`로 정확히 갈리는데 아무도 읽지 않았다. **안전장치가 순응한 사용자를 벌하면 사람들은 그것을 끈다.**

## Local Setup

Backend:

```bash
python -m compileall backend
uvicorn backend.main:app --reload
python scripts/run_product_smoke.py --base-url http://127.0.0.1:8000   # 16개 검사
```

`backend/main.py`는 `main_parts/*.part`를 import 시점에 조립한다. 테스트는 모듈을 직접 import하므로 조립이 깨져도 알 수 없다 — **스위트가 통과한다는 것과 앱이 뜬다는 것은 다른 주장이다.** 그래서 [product 워크플로](.github/workflows/product.yml)가 매 push마다 서버를 띄우고 이 스모크를 돌린다. 스모크가 **실패할 줄 아는지** 먼저 확인한 뒤에 신뢰한다 — 아무것도 듣고 있지 않은 포트를 향해 한 번 돌려 실패하는 것을 보고, 그 다음에 진짜 서버를 친다.

## Current Limitations

- ModelMate는 full enterprise AutoML 또는 full MLOps 플랫폼이 아닙니다.
- 현재 핵심 범위는 tabular CSV 기반 classification/regression 예측 분석입니다.
- time-series는 명확한 날짜/예측 기간 정보가 있을 때 제한적으로만 다룹니다.
- SHAP/feature importance는 feature contribution 설명이며 causality를 의미하지 않습니다.
- LLM planner는 optional이며, 기본 흐름은 deterministic planner로 동작합니다.
- prediction API, monitoring, feedback, pilot inquiry는 MVP 수준의 기반 기능입니다.
- billing, enterprise SSO, full RBAC, feature store, 자동 재학습 루프는 아직 구현 범위 밖입니다.

## Portfolio Notes

이 프로젝트의 핵심은 단순히 머신러닝 모델을 학습하는 것이 아니라, CSV 데이터가 실제 제품 흐름 안에서 분석, 보고서, API로 재사용되는 과정을 설계하고 구현한 것입니다. 이를 위해 데이터 업로드, 타깃 추천, 모델 비교, 설명 가능한 결과, 프로젝트 저장, 실행 기록, 예측 API, 사용량 제한, 오류 추적, 피드백 수집까지 SaaS MVP 관점의 기능을 단계적으로 확장했습니다.

## 배포 이력

Railway에 배포해 운영했다. 그 인스턴스는 **무료 플랜 만료로 지금은 내려가 있고**, 링크를 남겨두면 방문자가 `Application not found`를 만나므로 지웠다 — 죽은 링크는 없는 링크보다 나쁘다.

배포 설정 자체는 저장소에 남아 있어 다시 띄울 수 있다: [`railway.toml`](railway.toml), [`Procfile`](Procfile), [`nixpacks.toml`](nixpacks.toml).

문서 안 링크도 같이 정리했다. `docs/` 일곱 문서가 그 죽은 주소를 그대로 들고 있었다 — **한 파일에서 원칙을 말하고 일곱 파일에서 어기고 있었다.** 따라 하라고 적힌 QA 명령은 로컬 주소로 바꿔 지금 실제로 동작하고, 과거 실행 보고서는 기록으로 선언했다. `tests/test_no_dead_deployment_links.py`가 다시 들어오는 것을 막는다 — 네트워크를 쓰지 않는다. 인터넷이 끊긴 CI에서 조용히 통과하는 검사는 검사가 아니다.

## 무엇이 잘못됐고 어떻게 알았나

### 모르는 사람 둘이 서로의 업로드를 본다 — 적어둔 결정의 값

앞 절에서 **읽기**만 쟀다(매개변수 없는 `GET` 28개). 쓰기는 안 봤고, `/api/history`의
`DELETE`는 우연히 걸린 것이다. 이번에 **쓰기 30개**를 인증 없이 두드렸다.

    인증 없이 200/201   4개   전부 의도된 공개(로그아웃 · 프런트 오류 보고 ·
                              세션 초기화 · 게스트 세션 시작)
    401/403 거절        4개
    400/422            22개

**그 22개가 답을 가린다.** 빈 몸통이면 검증이 인증보다 먼저 걸린다. 유효한 입력으로
다시 두드리니 **`/api/upload`가 200**이었다 — 계정 없이 데이터셋이 올라간다.

**결함은 아니었다.** 익명도 요금제 `free`를 받고 한도가 실제로 걸린다(10억 행 →
`429 max_rows_per_dataset`), `datasets` 표에 행도 안 생긴다. **자원 소모는 막혀 있다.**

갈리지 않은 것은 상태다. 재현했다.

    A(익명)  POST /api/upload   환자기록.csv → 200
    B(익명)  GET  /api/columns  → 200  ['환자ID', '진단코드', '결과']
    C(게스트) GET  /api/columns  → 400  (자기 버킷은 비어 있다)

`_scope_state_to_the_caller`가 *"Anything unauthenticated falls into the shared
default"*라고 **적어둔 결정**이다. 결정은 적혀 있었고 **그것이 무슨 뜻인지는 안 적혀
있었다.** 고치지 않고 — 그건 사람 몫의 제품 결정이다 — **눈에 보이게 만들었다.**
바꾸기로 하면 그 검사가 빨간불이 되고, 무엇이 바뀌는지 그 파일이 말해준다.

**막을 장치는 이미 있다**: 게스트 세션 하나면 갈린다. 프런트는 언제나 그것을 보낸다.

### 가짜로 넣은 신원은 그것을 읽는 겹에만 보인다

로그인한 사용자도 격리되는지 보려고 `app.dependency_overrides`로 사용자를 넣었더니
**200**이 나왔다. 격리가 깨진 줄 알았다.

아니었다. 범위를 정하는 것은 **미들웨어**이고, 그것은 `get_current_user`를 의존성
주입이 아니라 **직접 부른다.** 오버라이드가 범위에 아무 영향이 없었다. 헤더에 진짜
토큰을 실으니 400 — 갈려 있다.



### 인증 없이 실험 기록 43건을 읽고, 지울 수 있었다

앞 절에서 이 저장소의 검사가 **전부 핸들러를 직접 부른다**는 것을 알았다. 그러면
`user=Depends(get_current_user)`가 한 번도 안 돈다 — 검사가 `user=OWNER`를 직접 넣기
때문이다. 그게 무엇을 가리는지 재봤다.

`get_current_user`는 **자격이 없으면 `None`을 돌려준다.** 막지 않는다. 선언과 확인은
다른 일인데, 검사는 둘 다 안 본다.

`TestClient`로 매개변수 없는 `GET` 28개에 인증 없이 요청했다: **401/403 거절 11 ·
400(상태 없음) 6 · 200 응답 11.** 열하나 중 열은 괜찮았다(`/api/health`, 준비 상태,
그리고 **빈 목록** — `/api/projects`와 `/api/deployed`는 2바이트다).

**`/api/history`가 45,506바이트를 줬다.** 43건 — 타깃 컬럼명, 데이터 크기, 모델 점수.
`experiment_history.json`, 인증 이전 시절의 **공용 파일**이다. `DELETE`도 같은 갈래를
지나 **그 파일을 지웠다.** `ok: True`와 함께. 둘 다 아무도 결정한 적 없다.

### 그 갈래에 검사가 있었고, 통과하고 있었다

`test_an_anonymous_caller_sees_nothing_of_either`가 DB에 심은 무작위 표식이 응답에
없는지를 봤다. 그런데 **익명 갈래는 DB를 아예 안 읽는다** — 파일을 돌려주니 DB 표식이
들어갈 리가 없고 단언은 언제나 참이었다.

**"아무도 안 봤다"가 아니라 "본 것이 다른 것이었다."** 앱을 통과시켜 보고서야 알았다.

프런트는 언제나 토큰이나 게스트 세션 헤더를 보내므로 이 갈래에 오는 것은 이 제품의
클라이언트가 아니다. **401**로 바꿨다 — 조용히 빈 목록을 주면 "기록이 없다"로 읽힌다.

### 공개 표면을 이름으로 뒀다

인증 없이 200을 주는 것이 무엇인지 아무 데도 적혀 있지 않았다. 새 라우트가 의존을
빼먹어도 검사는 전부 통과한다. 이제 목록이 정확히 일치해야 하고, 각 항목에 이유가 있다.

**공용 `STATE` 버킷은 고치지 않았다.** `_scope_state_to_the_caller`가 *"Anything
unauthenticated falls into the shared default"*라고 적어두고 있다 — 결함이 아니라
적어둔 결정이다. 그 결정이 무엇을 뜻하는지만 검사로 고정했다.



### 마지막 한 겹을 시험하는 것이 하나도 없었다

여러 절에 걸쳐 거부를 세고 또 셌다 — `raise HTTPException` 108개, 비-HTTP raise 7개.
**그 밑에 한 겹이 더 있었다.** 미들웨어가 잡지 못한 예외를 전부 받아 응답을 만들고
기록을 남긴다.

    사용자   500 "예상하지 못한 내부 오류" + error_id + "관리자에게 전달하세요"
    운영자   monitoring_events에 route·method·status·진짜 메시지

**그 겹을 시험하는 것이 없었다.** 검사 1,021개는 전부 핸들러를 직접 부른다 —
`TestClient`를 쓰는 파일이 **0개**였다. 미들웨어는 요청이 앱을 통과할 때만 도는데
통과하는 검사가 없었다. 기록도 그 사실을 말한다: `error_code='internal_error'` 행이
**0건**이다.

**응답이 시키는 대로 해봤다.** "관리자에게 error ID를 전달하세요" — 그 id로 관리자가
조회할 수 있는가. **이어져 있었다.** 설계는 멀쩡했고 확인만 없었다. *빈손도 결과지만,
확인한 뒤에야 그렇게 말할 수 있다.*

이제 열 개가 그 겹을 지킨다: 사용자는 내부 문장을 못 받고, 운영자는 받고,
`error_id`는 헤더에도 있고, 기록이 **실제로 한 줄 늘어나는지**까지 센다.

### 그리고 보안 검사를 쓰다 하마터면 아무것도 시험하지 않을 뻔했다

`../../etc/passwd`를 샘플 경로에 보내고 **200을 받았다.** 취약점이 아니라 클라이언트가
URL을 정규화해서 `/etc/passwd/download`로 보냈고 SPA 캐치올이 index.html을 준 것이다.
**요청이 그 라우트에 닿지도 않았다.**

그렇게 쓴 보안 검사는 통과하면서 아무것도 시험하지 않는다. **심은 것이 서버에
도착했는지부터 봐야 한다.**



### 이미 사용자를 향해 쓰인 문장이 배관에서 버려지고 있었다

앞 절에서 맨 `ValueError`가 500이 되는 것을 한 자리 고쳤다. **내가 세어온 거부 108개
목록에는 그런 것이 아예 없었다** — `raise HTTPException`만 셌기 때문이다. 다시 셌다.

    backend 전체의 비-HTTPException raise    7개
      resolve_jwt_secret          부팅 거부. 요청 경로가 아니다
      create_goal_first_agent_run **진짜 내부 실패.** 500이 맞다
      _fallback_from_state ×2     같은 모듈 안에서 잡힌다
      execute_agent_run           앞 절에서 409로 고쳤다
      make_cv_for_target ×2       ← **여기**

`make_cv_for_target`의 둘은 **이미 사용자를 향해 쓰여 있다.**

    "학습할 데이터가 너무 적습니다."
    "일부 정답 값의 데이터가 1개뿐이라 교차검증을 할 수 없습니다."

세 호출 자리 어디도 안 잡아서 전역 처리기까지 올라갔고, 사용자는 **500 "예상하지 못한
내부 오류 — 잠시 후 다시 시도하거나 관리자에게"**를 받았다. **정답 클래스 하나에 행이
하나뿐인 CSV는 흔하다.** 재현해서 확인했다.

*문장은 이미 쓰여 있었고 배관이 그것을 버리고 있었다.*

한 곳에서 변환한다(`cv_for_target_or_refuse`). 세 자리에 각각 `try/except`를 쓰면 같은
사실을 세 번 적는 꼴이다. **`str(error)`를 그대로 싣지도 않는다** — 아는 문구만
통과시키고 나머지는 일반 문장으로 바꾼다. sklearn이 던지는 것이 늘면 그 문구가 그대로
나가고, 그건 앞 절의 `run_shap` 결함이다.

### 그리고 정확한 수로 박아둔 못을 하한선으로 되돌렸다

`failure_detail` 호출 수를 `== 12`로 박아뒀었다. **두 회차 연속으로 좋은 변경에
빨간불이 켜졌고**, 고칠 것은 매번 숫자 하나였다.

하한선을 비판해온 근거("하나가 빠지는 것을 못 본다")를 여기 대보면 성립하지 않는다 —
그 실패는 **바로 위 `test_there_are_none`이 잡는다.** 정확한 수가 추가로 지키는 것은
없고 막는 것은 관례를 넓히는 변경뿐이었다. **다른 검사가 그 실패를 이미 덮고 있으면
정확한 수는 값이 아니라 마찰이다.**



### 계획 없는 실행을 돌리면 "예상하지 못한 내부 오류"가 났다

에이전트 라우트 여섯의 `404`가 한 번도 안 돌아서 돌려보려 했다. **둘 다 예상과 달랐다.**

**넷은 돌릴 수 없었다.** 행은 있고 계획도 단계도 없는 실행을 만들어 불러보니 **전부
dict를 돌려준다** — 조회 함수가 소유자의 실재하는 행에 대해서는 빈 값을 주지 않는다.
그 `if not result: 404`는 **관문을 지난 뒤 조회 사이에 행이 사라졌을 때**를 막는
경쟁 구간 방어선이다. 억지로 돌리는 검사를 지어내지 않고 **이름으로 뒀다** —
`delete_deployed`의 403에서 배운 것이다: *도달하지 않는 것과 쓸모없는 것은 다르다.*

**`execute`는 달랐다.** `execute_agent_run`이 맨 `ValueError`를 올리고, 전역 처리기가
그것을 **500 "예상하지 못한 내부 오류 — 잠시 후 다시 시도하거나 관리자에게"**로 바꾼다.

**완전히 예상되는 상태를 예상하지 못한 오류로 보고한 것이다.** 새어 나가는 정보는
없었지만(전역 처리기가 가린다) **안내가 틀렸다** — 기다린다고 계획이 생기지 않는다.
`409`로 바꿨다: 실행은 있고 없는 것은 그 안의 계획이라 `404`는 맞지 않고, 이 저장소는
"지금 하면 안 된다"를 `409`로 쓴다.

**그리고 앞서 박아둔 못이 내 변경을 잡았다.** `failure_detail` 호출 수를 정확히
고정해 둔 검사가 빨간불이 되며 *"늘어난 것은 좋고, 줄었다면 무엇이 그 자리를
대신하는지 보라"*고 말했다. 시킨 대로 12를 13으로 고쳤다.



### 도달하는데 아무도 확인하지 않는 거부 — 여섯

거부에는 세 가지 상태가 있고 **초록불은 셋을 구별하지 않는다.**

    한 번도 도달하지 않는다      커버리지가 말해준다
    도달하고 확인된다            바꾸면 검사가 빨간불이 된다
    **도달하는데 확인되지 않는다**  ← 커버리지는 "돌았다"고 하고 검사는 통과한다

가운데와 마지막이 화면에서 같아 보인다. 재는 도구를 만들었다
(`scripts/find_unasserted_refusals.py`): 스위트를 한 번 돌리며 어느 검사가 어느
`raise`를 지나는지 적고, **지점마다 상태를 599로 바꿔 그 지점을 지나는 검사만**
다시 돌린다. 여전히 통과하면 그 지점은 확인되지 않는 것이다.

**여섯이 나왔다.** 넷은 `assert status_code != 410` 같은 **부정 단언**이 지나가는
자리였다 — *"이건 아니다"는 무엇이 왔는지 묻지 않는다.* 둘은
`pytest.raises(Exception)`이었다 — **예외판 `!=`다.** 그중 하나는 이름이
`test_enforce_limit_raises_when_over`인데 무엇을 raise하는지는 확인한 적이 없었다.

### 그리고 그 도구가 여섯을 못 보고 있었다

처음 판은 `raise HTTPException(...)`만 셌다. **102개.** 그런데
`usage_limit_error`는 HTTPException을 *돌려주는* 헬퍼라 호출자들은
`raise usage_limit_error(...)`로 쓴다 — **그 여섯이 통째로 안 보였다.** 사용량 한도
`429`는 요금제를 지키는 자리다. 공장을 거치는 것까지 세게 고치니 **108개**가 됐고,
다시 재니 **그 여섯 중 둘이 확인되지 않고 있었다.**

도구가 못 잰 것은 `0`으로 세지 않고 **"재지 못한 지점"으로 따로 찍는다** — 조용히
빼면 이 도구도 초록불이 된다.



### 남의 예측 API 토큰을 취소할 수 있는지 아무도 확인한 적이 없었다

CI가 한 번도 발동시키지 않는 거부 **53개** 중 `404`가 열다섯이다. 여섯을 골랐다 —
관리자 전용 조회 넷과 **예측 API 토큰의 취소·재발급 둘.**

뒤의 둘이 요점이다. 예측 API 토큰은 배포된 모델을 부르는 열쇠이고, 취소 질의는
`WHERE token_id=? AND project_id=? AND owner_user_id=?`로 좁혀져 있다.
**그 조건이 지워져도 지금까지는 아무 검사도 빨간불이 되지 않았다.**

**그리고 첫 검사는 그 줄을 지나지도 않았다.** "남이 취소하려 하면 404"를 썼는데,
대조에서 토큰 줄의 `404`를 `403`으로 바꿔도 초록불이었다 — `assert_project_owner`가
**먼저** 끊기 때문이다. 단언은 맞지만 **이름이 말하는 자리를 지나지 않는다.**

고쳐서 남이 **자기 프로젝트를 가지고** 남의 토큰 id를 부르게 했다. 그러면 프로젝트
관문은 통과하고, 막는 것은 토큰 질의뿐이다. 이제 그 줄을 `403`으로 바꾸면 빨간불이 된다.

**상태 값을 검사에 베껴 적었다가 400을 받았다.** `"triaged"`는 이 제품의 피드백 상태가
아니다. 코드가 쓰는 집합에서 꺼내 쓰게 고쳤다 — 검사가 상수를 손으로 베끼면 제품이
바뀔 때 검사만 낡고, 그 상태로 초록불이 된다.



### CI가 한 줄도 실행하지 않던 라우트가 이제 0개다

라우트 감사가 아홉을 남겼고 일곱은 앞 절에서 닫았다. 둘은 **상태를 갖춰야 도달한다**고
적어두고 넘어갔다 — `predict_single`(31줄)과 `retry_agent_step_api`(7줄).

그 사이에 둘 다 만들 방법이 생겼다: `STATE`를 되돌리는 픽스처와
`ensure_agent_trace_schema`. **막혀서 남긴 것이 아니라 도구가 없어서 남긴 것이었다.**

    predict_single         본문 31줄 · 0 → 28
    retry_agent_step_api   본문  7줄 · 0 → 7
    라우트 100개 중 죽은 것  9 → **0**

`0`이라는 숫자는 한 번 속은 적이 있어서(데코레이터 줄을 세고 있었다) **세는 쪽을
대조했다** — 살아 있는 라우트 하나를 죽은 것으로 심으니 그것을 집어낸다.

**덤으로 제품 결정 하나를 문서로 만들었다.** `predict_single`은 사용자가 보내지 않은
값을 조용히 채운다 — 범주형은 `0`, 수치형은 **학습 데이터의 평균.** 읽을 수 없는 값도
마찬가지다. 그러면 응답은 **사용자가 보내지 않은 값으로 계산된 예측**인데 어디에도
그렇게 적혀 있지 않다. 거절할지 채우되 알릴지는 사람이 정할 일이라, 지금 무엇을
하는지만 고정했다 — 바꾸는 날 그 검사가 빨간불이 되고 그때 이 문장을 다시 읽게 된다.



### 설명이 실패하면 클라이언트가 파일 경로를 받았다

CI가 한 번도 발동시키지 않는 거부를 종류별로 훑다가 `500` 여섯을 봤다. 다섯은
`failure_detail(...)`로 말할 것과 안 말할 것을 가려서 내보낸다. 하나가 이랬다.

    raise HTTPException(500, str(e))          030_shap.part, `run_shap`

재현했다. 클라이언트가 받는 것:

    cannot load artifact: /home/jovyan/work/modelmate/models/u-42/best.pkl (uid=1000)

**절대 경로와 uid가 그대로 나간다.** 이 저장소는 `GET /api/debug-env`로 환경 노출을
한 번 겪었고 그 자리를 지키는 검사가 있는데, **예외 문자열로 나가는 길은 아무도 안
보고 있었다.**

이 줄이 왜 살아남았는지가 요점이다. **안 도는 줄이었다** — 안쪽 되돌림(계수 기반
중요도)까지 실패해야 여기 닿는다. 커버리지에도, 거부 감사에도 안 걸렸다.

숨기는 것이 아니라 **옮겼다.** 예외 종류(`error_type=RuntimeError`)는 화면에 띄워도
되는 만큼이라 남기고, 진짜 메시지는 보안 기록으로 보낸다. 그리고 같은 모양이 **다른
라우트에 새로 생기지 않도록** 구조 검사를 함께 뒀다.

**세다가 내 수를 한 번 틀렸다.** "스물넷이 `failure_detail`"이라고 적었는데 여덟이다 —
인라인 dict와 헬퍼가 만든 것까지 한 덩어리로 셌다. 형태별로 다시 셌다: 문자열 리터럴
70 · 인라인 dict 17 · `failure_detail` 8 · 변수에 담긴 구조체 7 · **예외 문자열 1.**



### 소유권 관문 검사 넷이 CI에서 한 번도 돈 적이 없다

CI 로그는 `951 passed, 4 skipped`였다. 넷이 무엇인지 봤다.

    tests/test_ownership_gates_refuse_other_users.py
    reason: analysis_runs는 에이전트 경로가 처음 쓸 때 만들어진다

**남의 분석 실행에 접근하면 거절하는지를 보는 검사들이다.** `analysis_runs`는 에이전트
경로가 처음 쓸 때 만들어지므로 **갓 만든 DB에는 없다** — 즉 CI에는 늘 없다. 개발
기계에는 예전 실행이 남긴 표가 있어서 로컬에서는 넷이 돌았고, **정작 지켜야 할 곳에서는
안 돌았다.** 초록불이었고, 통과한다고 믿고 있었다.

건너뛸 이유가 없었다. **스키마를 만드는 함수가 이미 있다**(`ensure_agent_trace_schema`).
없으면 만들고, 그래도 못 만들면 그때 건너뛴다 — 그리고 그 사실이 화면에 남는다.

DB를 지우고 갓 만든 상태에서 확인했다: **16개 전부 통과, skip 0.** 소유권 관문의
거절을 꺼보니 빨간불이 된다.


### 거절인데 한 번도 터진 적 없는 것 — 66개 중 상태를 지키는 여섯을 닫았다

`HTTPException` 발생 지점 102개 중 CI(pytest + 스모크 열다섯)에서 **한 번도 안 터지는
것이 66개**였다. 한 회차에 다 할 수 없어 종류로 잘랐다.

    400 × 34   입력 모양이 틀렸다        — 사용자가 다시 보내면 그만이다
    404 × 17   없거나 남의 것이다
    409 ×  5   **지금 하면 안 된다**      ← 여기
    410 ×  2   **꺼진 API다**            ← 여기
    413 ×  1   **너무 크다**             ← 여기
    500 ×  6   서버가 졌다

입력 검증이 아니라 **상태를 지키는 거절**을 골랐다. 여기가 틀리면 사용자는 요청을
고치는 게 아니라 **돌고 있는 작업이 딸린 데이터셋을 지우거나, 꺼놨다고 믿은 예측 API가
계속 응답한다.**

`/api/v1/{id}/predict`와 `/api/v2/{id}/predict`는 **쌍둥이**다. 둘 다 각자
`disabled_at`을 본다 — 한쪽만 검사하면 다른 쪽이 조용히 갈라지고, 그때 껐다고 믿은
API가 옛 경로로 계속 답한다. 둘이 **같은 답을 하는지**까지 본다.

**사슬도 함께 본다.** 데이터셋을 지우면 그것을 쓰던 배포 모델이 `disabled_at`을 받고,
그다음 예측 호출이 410이 된다. 조각을 따로 확인하면 **사슬이 끊겨도 둘 다 초록불**이다.

### 내가 쓴 검사가 이 저장소의 단골 결함을 저질렀다

413 검사를 처음엔 이렇게 썼다 — **라우트 본문의 크기 계산을 테스트 파일에 옮겨 적고
그 사본을 시험했다.** `UploadFile`을 만들기 귀찮다는 이유였다. 그건 이 저장소가 계속
찾아온 바로 그 모양이다: **한 사실을 두 곳에 적고 한 곳만 지키는 것.** 제품의 한도
계산이 바뀌어도 내 사본은 통과했을 것이다. 지우고 진짜 라우트를 부른다.

### `in (404, 409)`로 써둔 검사는 409에 닿은 적이 없었다

재실행 거절 검사를 `in (404, 409)`로 뒀는데, **실제로 나온 것은 늘 404였다** —
픽스처가 만든 행을 목록 함수가 아예 못 봤다. 기록의 프로젝트는
`data.dataset_ref.project_id`에서 오고 `analysis_run_id`는 JSON이 아니라 **행 번호**로
만들어진다. **둘 중 아무거나면 통과인 단언은 닿지 않은 것을 닿은 것처럼 보이게 한다.**
픽스처를 고치고, "기록이 목록에 실제로 보이는가"를 먼저 확인하는 대조를 앞에 뒀다.

### 소프트 삭제를 하드 삭제로 착각했다

`delete_dataset`이 행을 지운다고 가정하고 검사 둘을 썼다가 빨간불이었다. 코드가 아니라
내 가정이 틀렸다 — `deleted_at`을 찍고 `retention_status='deleted_retained'`로 남긴다.
**검사가 빨간불일 때 검사를 고치는 것과 가정을 고치는 것은 다르다.**



### CI가 한 줄도 실행하지 않던 라우트 — 마흔이라 적혀 있었고 아홉이었다

로드맵에 **마흔 개**, 그 뒤 "프런트가 부르는 스물넷 중 열일곱이 남았다"고 적혀 있었다.
pytest와 **스모크 열다섯을 합쳐** 다시 쟀다 — CI가 실제로 돌리는 것 전부로.

    라우트 핸들러 100개 중 본문이 한 줄도 안 도는 것   9개

스모크 열둘을 CI에 넣은 것이 대부분을 닫았고 **로드맵의 숫자만 그대로 있었다.**

**처음 잰 결과는 0개였다.** 너무 좋아서 다시 봤더니 `ast.walk(node)`가 데코레이터
노드까지 판다 — `@app.post(...)` 줄은 import 때 반드시 실행되므로 **모든 라우트가
"돌았다"로** 나왔다. 본문만 세도록 고쳐 아홉이 됐다.

아홉 중 **둘이 사용자 데이터를 지우는 `DELETE`**였다. `clear_history`(관리자면 전원의
기록을 지운다)와 `delete_deployed`. 앞 절에서 연결 누수를 고치느라 손댄 바로 그 둘이고,
**그때 나는 아무것도 실행하지 않는 코드를 고치고 있었다.** 일곱에 검사를 붙였다.

### 지워진 라우트가 다음 파일에 `return` 한 줄을 남겼다

`GET /api/debug-env`를 지웠을 때 **그 `return` 줄이 다음 조각 맨 앞에 남았다.**
조각들은 이어 붙여 컴파일되므로 그 고아 한 줄은 아무 상관 없는 `reset_session`의
본문 끝에 붙었다.

```python
async def reset_session(user=...):
    STATE.clear()
    return {"ok": True}
    return {"key_length": ..., "all_env_keys": all_keys}   # ← 도달할 수 없다
```

죽은 줄이라 실행되지 않고, 그래서 `test_no_environment_disclosure.py`도 못 봤다.
하지만 읽는 사람에게는 **환경을 뱉는 라우트로 보이고**, 위 한 줄이 지워지면 실제로
그렇게 된다. **지운 곳과 남은 곳이 다른 파일이었다는 것**이 이것이 두 달 산 이유다.
조립된 프로그램 전체에서 `return`/`raise` 뒤 문장을 훑는 검사를 넣었다 — 하나뿐이었고,
그 하나가 이것이다.

### 죽은 코드라고 부르려다 대조가 뒤집었다

`delete_deployed` 안에 소유권 검사가 **하나 더** 있다. 403을 낸다. 재보니 남이
접근하면 앞의 `assert_deployed_model_owner`가 먼저 **404**로 끊어서 **그 403은 한 번도
안 터진다.** 죽은 코드라 지우려 했다.

**관문의 거절을 지우고 돌렸더니 인라인 검사가 403으로 막았다.** 죽은 게 아니라
관문이 맞는 동안에만 안 도는 것이고, 그게 이중 방어가 뜻하는 바다. **지우지 않았다.**



### 시계가 둘이었고, 그것을 세던 검사기는 파일 열둘을 안 보고 있었다

    datetime.now()      32곳   표시자 없음   2026-08-23T19:00:00.123456
    datetime.utcnow()    3곳   "Z" 붙음      2026-08-23T10:00:00Z

`utcnow()`를 쓰는 셋은 나중에 붙은 에이전트 하위 모듈이다. **새 모듈이 더 나은
규칙을 골랐고, 옛 것과 만나는 자리를 아무도 안 봤다.** 만나는 자리는 프로젝트 실행
목록이었다 — `_project_runs`가 `experiments`(로컬 시계)와 `analysis_runs`(UTC 시계)를
합친 뒤 **문자열로** 정렬한다. 목록에는 "최신순"이라고 적혀 있다.

**오프셋이 0이어도 뒤집힌다.** 두 시계는 자릿수도 다르다 — `experiments`는 마이크로초
까지, `analysis_runs`는 `timespec="seconds"`. 같은 초 안에서 `'.'`(0x2E)가 `'Z'`(0x5A)
보다 앞이라 나중 것이 아래로 간다.

**클라이언트에서는 못 고친다.** 프런트도 같은 문자열 정렬을 세 곳에서 하지만,
표시자 없는 값을 브라우저는 **보는 사람의 시간대**로 읽는다 — `Date.parse`로 바꾸면
오류가 옮겨갈 뿐이다. 고칠 수 있는 곳은 그 값을 쓴 서버뿐이다.

한 곳을 고치고 **다른 한 곳을 잊었다** — `_project_reports`가 같은 값을 복사해 와서
다시 문자열 정렬한다. 검사가 잡았다.

**그리고 검사기가 파일 열둘을 안 보고 있었다.** 시계 수를 세다 줄 훑기 32와 AST 28이
안 맞아 이유를 봤다. `main.py`는 조각을 이어 붙여 한 번에 컴파일하므로 **조각 하나하나는
파이썬 파일이 아니다** — 열둘은 단독으로 파싱되지 않는다. 구조 검사들이
`except SyntaxError: continue`로 넘기고 있었다.

    숨어 있던 무보호 쓰기 3개   deploy_model · delete_deployed · deploy_model_stable
    숨어 있던 타입 없는 except 7개

**앞 두 절이 발표한 수가 둘 다 틀렸다** — "쓰기 22개"는 25개, "타입 없는 `except:`
2개"는 9개였다. 위 두 절을 고쳤다. 맞는 처리는 이 저장소에 이미 있었다:
`test_declared_dependencies.py`가 같은 자리에서 건너뛰지 않고 줄 훑기로 되돌아가며
*"건너뛰는 것이야말로 이 모듈이 막으려는 실패"*라고 적어 뒀다. 그 파일에만 있었다.

이제 `tests/part_source.py`가 조립해서 파싱하고 줄 번호를 조각으로 되돌린다. 파싱이
실패하면 **건너뛰지 않고 죽는다.**



### 삼킨 예외가 어디까지 조용한가

앞 항목에서 `auth_logout`이 **세션 취소에 실패해도 `ok: True`를 돌려주고 아무 데도
남기지 않는 것**을 고쳤다. 하나를 고쳤으면 나머지를 센다.

    예외 객체를 아예 버리는 처리기   44개
    그중 `pass`로 흘려보내는 것       8개
    타입 없는 `except:`               2개

**타입 없는 `except:` 둘은 둘 다 오래 걸리는 자리에 있었다** — CSV 파싱과, 모델을
차례로 학습해 보는 되돌림 고리. 즉 사람이 실제로 Ctrl-C를 누르는 자리다. 거기서
`KeyboardInterrupt`는 중단이 아니라 "읽을 수 없는 파일"과 "다음 모델"로 읽혔다.

**`sqlite3.OperationalError`를 통째로 삼킨 세 곳.** "표가 아직 없을 수 있다"를
견디려던 것인데, 직접 일으켜 보니 같은 예외 클래스가 `no such column`(이 파일이
컬럼을 추가한다)과 `database is locked`(앞 항목에서 고친 바로 그 실패)도 나른다.
삼키면 화면은 **"이 프로젝트에 작업이 없습니다"**라고 말한다 — 작업이 있는데도.
맞는 방법은 같은 파일 200줄 위 `add_column_once`에 이미 있었다: 예상한 메시지만
넘기고 나머지는 올린다.

**`FREE_MAX_DATASETS=three`은 조용히 무시됐다.** 운영자는 자기가 넣은 값이 걸려
있다고 믿고 실제로는 기본값이 걸린다. 응답은 그대로 두고 기록에 남긴다.

남긴 다섯은 일부러 남긴 것이고, **그것을 검사로 만들었더니 넷이 걸렸다** — 이유가
내 머릿속에만 있었고 코드에는 없었다. 그 코드를 읽는 사람은 의도해서 삼킨 것과 잊고
삼킨 것을 구별할 수 없다. `tests/test_swallowed_errors_are_not_silent.py`.



### 그 모양이 몇 군데나 있는지 셌다

앞 절의 결함 — 예외가 나면 DB 연결이 열린 채 남고 쓰기 잠금이 풀리지 않는 것 — 을 고친 뒤 **나머지를 셌다.** 이 프로젝트가 반복해서 놓치는 자리다: 규칙을 세우고 한 곳에 적용한 뒤 나머지를 세어보지 않는 것.

    `get_db()`를 여는 함수            87개
    예외에 연결이 남을 수 있는 것       28개
    그중 **쓰기를 하는 것 25개**        ← 잠금을 쥔다

읽기만 하는 것도 연결을 새지만 쓰기 잠금은 쥐지 않는다. 위험의 크기가 다르므로 구분해서 셌다.

**처음에는 스물둘로 셌다.** 뒤 회차에 검사기를 고치고 나니 스물다섯이었다 — 조각을 하나씩 `ast.parse`하면서 `except SyntaxError: continue`로 넘겼는데, 조각 열둘은 단독으로 파싱되지 않는다(앞 조각에서 시작한 함수 본문이 이어진다). **열두 파일이 조용히 빠졌고 화면에서는 "이상 없음"과 같아 보였다.** 숨어 있던 셋은 부팅 시 DDL이 아니라 `deploy_model`·`delete_deployed`·`deploy_model_stable` — **사용자가 닿는 배포 엔드포인트**다. `tests/part_source.py`에 이유와 함께 적었다.

**한 번에 고치지 않았다.** 배포된 앱의 함수 스물다섯을 기계적으로 감싸는 것은 그 회차에 감당할 위험이 아니고, 각 함수의 조기 반환·예외 경로가 제각각이다. **인증 없이 도달하는 쓰기 넷**을 고쳤다 — `auth_google`(앞 절), `auth_signup`, `auth_login`, `auth_logout`. 바깥에서 입력을 넣어 예외를 만들 수 있는 자리다.

**그다음 회차에 열둘을 더 고쳤다.** 남은 스물하나를 도달 경로로 분류했더니 **사용자가 닿는 것이 열둘**이었다 — 라우트가 직접 다섯, 라우트에서 불리는 것 다섯, 그것들에서 불리는 것 둘. 앞 회차에는 새로 찾은 셋만 "급하다"고 적고 나머지를 분류하지 않았다.

손으로 열둘을 고치는 대신 **검증할 수 있는 변환**을 썼다: `conn = get_db()` 뒤 같은 블록을 감싸고, 새 `try`를 도로 벗겨내 AST가 글자 하나까지 같은지 확인한다. 그 확인이 두 번 일했다 — `make_token`의 세겹따옴표 SQL **안쪽 줄까지 들여쓰기가 밀려** 문자열 내용이 바뀐 것을 잡았고, `deploy_model`은 **함수가 조각 두 개에 걸쳐 있어** 시작 파일만 훑던 변환에 안 보였다. 그리고 **못 잡은 것도 있다**: 같은 함수를 두 번 감싸도 통과했다(벗겨내는 쪽이 조건에 맞는 `try`를 전부 벗기므로). 일곱 개가 이중으로 감싸진 뒤에 알았고, 멱등성 검사를 따로 넣었다.

`auth_logout`에서 덤으로 하나 더 나왔다. 바깥이 `except Exception: pass`여서 **세션 취소가 실패해도 응답은 `ok: True`였고 어디에도 남지 않았다.** 응답은 그대로 뒀다 — 로그아웃을 실패로 돌려주면 사용자가 토큰을 쥔 채 화면에 남는다. 대신 보안 기록에 적는다.

남은 **아홉은 전부** 표를 만드는 부팅 시 DDL(`ensure_*`, `init_db`)이다. 거기서 예외가 나면 부팅이 실패해 프로세스가 어차피 못 뜬다 — 잠금을 쥔 채 서비스가 계속되는 상황이 아니다. **위험의 종류가 달라서 남긴다.** 목록이 아니라 그 성질을 검사로 지킨다: 남은 목록에 DDL이 아닌 것이 들어오면 걸린다. 고치는 것이 맞지만 **어디가 남았는지 아는 채로 두는 것이 먼저다** — 목록이 정확히 일치해야 하므로 새로 생기는 것도, 고쳐서 빠지는 것도 걸린다.

### 구글 로그인이 DB를 잠근 채 남길 수 있었다

프런트가 부르는데 CI가 한 줄도 실행하지 않던 라우트 중 하나다. 로그인 **이전**에 도달하고 여기서 역할이 정해진다.

검사를 쓰다 진짜 결함이 나왔다. **비밀번호로 가입한 이메일과 같은 주소로 구글 로그인을 하면** `users_email_ci` 유니크 인덱스가 INSERT를 거절한다. 예전 코드는 그 예외를 그대로 올렸고 — 500 — **`conn.close()`가 마지막 줄에 있어 연결이 열린 채 남았다.** sqlite는 그 연결이 쥔 쓰기 잠금을 놓지 않으므로 **그 뒤 이 프로세스의 모든 쓰기가 `database is locked`로 죽는다.** 재현했다: 한 번 부딪히면 그 뒤 아무것도 못 썼다.

`try/finally`는 이 저장소의 관행이었다 — 워크스페이스 파일이 아홉 곳, 파일럿 문의가 세 곳에서 쓴다. **이 파일에만 없었다.**

충돌을 먼저 잡아 **409로 말한다.** 두 계정을 잇는 것은 여기서 결정하지 않았다 — 이메일 소유 증명 없이 이으면 계정 탈취 경로가 되고, 로그인 핸들러가 조용히 내릴 결정이 아니다. 무엇을 할지는 로드맵에 제품 결정으로 남겼다.

**승격 경로도 함께 고정했다.** 이 저장소는 관리자 승격에서 한 번 데였다(문서화된 목록을 무시하는 두 번째 시딩 경로). 구글 로그인은 **세 번째 경로**이고 확인된 적이 없었다 — 목록 밖 계정은 관리자가 되지 않고, 목록에 넣으면 되고, 이미 관리자인 계정은 강등되지 않고, 승격은 기록에 남는다.

**검사가 세 번 헛돌았다.** 같은 IP로 열 번 넘게 불러 인증 전 조임(429)에 걸렸고 — 그 통제는 제대로 돌고 있었다 — 호출자를 각각 다른 IP로 바꿨다. `finally`를 지웠는데도 통과해서 보니, 충돌을 먼저 잡은 뒤로는 **409 경로가 쓰기를 시작하지 않아** 연결이 남아도 잠기지 않는다. 구조로 고정하려 1,600자 창을 잘라 봤더니 **창이 옆 함수까지 덮어** 또 통과했다. AST로 `auth_google`의 `finally`만 보게 하고서야 물었다.

### 이 문서가 제품을 208번째 줄에서 말하고 있었다

회차마다 새 발견을 문서 **위쪽**에 덧붙였다. 각 회차에는 그것이 맞는 자리였고, 아무도 전체를 **처음 온 사람의 자리에서** 보지 않았다. 그래서 `## What It Does`가 208번째 줄에 있었다 — 읽는 사람은 제품을 알기 전에 발견 열넷을 지나야 했다.

형제 저장소 넷은 처음부터 제품을 앞세우고 있었다(각각 12~14절, 133~162줄). 여기만 38절 504줄로 자랐다 — **규모가 문제를 만든 것이지 규칙이 없어서가 아니다.** 이 저장소가 반복해서 찾아온 모양이기도 하다: 개별 변경은 각각 옳고, **합쳐진 결과를 보는 것이 없다.**

순서만 바꿨다. **한 글자도 지우지 않았고**, 낱말 단위로 세어 잃은 것이 없음을 확인했다. `tests/test_the_readme_leads_with_the_product.py`가 다시 뒤집히는 것을 막는다 — 맨 위에 절을 붙이거나, 발견 뒤에 제품 절을 붙이거나, 우산 제목을 바꾸면 실패한다.

아래는 이 저장소가 스스로에게서 찾은 것들이다. 각 절은 **무엇을 재봤고 무엇이 나왔는지**를
적는다 — 고친 것뿐 아니라 **빈손으로 끝난 확인**과 **뒤집은 판단**도 함께 남긴다.

이 절들이 원래 문서 맨 앞에 쌓여 있었다. 회차마다 새 발견을 위쪽에 덧붙였고, 그래서
`## What It Does`가 208번째 줄에 있었다 — **읽는 사람은 제품을 알기 전에 발견 열넷을
지나야 했다.** 2026-08-23에 순서만 바꿨다. 한 글자도 지우지 않았고, 형제 저장소 넷은
처음부터 제품을 앞세우고 있었다.

### 테스트 수를 내가 부풀렸다 — 되돌렸다

문서 검사를 문서마다 파라미터로 걸었더니 다섯 저장소에서 **119개가 늘었다.**
검사하는 성질은 5개인데 문서가 늘 때마다 숫자가 늘었다. modelmate는 한 파일이
88개를 만들어 427에서 515로 뛰었다.

이 저장소들은 README가 주장하는 테스트 수를 CI가 실제 수집 개수와 대조한다.
숫자가 두 번 어긋난 뒤에 만든 장치다. **그 숫자가 뜻을 가지려면 내가 먼저
부풀리지 말아야 한다.** 한 성질에 테스트 하나로 합치고, 어느 문서가 걸렸는지는
실패 메시지가 말하게 했다 — 파라미터 이름이 해주던 일이고, 그것 때문에 개수를
왜곡할 이유는 없다.

### Agent Mode가 절반에서 멈춰 있었다

README가 앞세우는 기능인데 **어떤 검사도 이 경로를 치지 않았다.** `backend/agents/executor.py`는 커버리지 9%였고, 앱을 띄워 스모크 13개를 전부 돌려도 움직이지 않았다 — 엔드포인트 12개가 있고 아무도 치지 않고 있었다.

돌려보니 사슬이 절반에서 멈춘다. 학습은 `AutoML training completed`로 성공 관측을 남기고, **바로 다음 설명 도구가 "Run AutoML training before explanation."으로 실패**한다. 같은 요청 안에서 한쪽은 썼고 한쪽은 못 읽었다.

원인은 스레드 경계였다. `automl_training_tool`은 이미 도는 이벤트 루프 안에서 호출되면 코루틴을 `ThreadPoolExecutor`로 넘기는데, **`ContextVar`는 스레드 경계를 넘지 않는다.** 새 스레드는 빈 문맥에서 시작해 기본 스코프를 읽고, 그래서 `set_target`과 `run_cv`가 **요청 버킷이 아니라 공유 기본 버킷**에 썼다.

**조용한 쪽이 더 나쁘다.** 요청별 격리를 넣은 이유가 정확히 그 공유 버킷을 없애는 것이었다 — A가 올린 데이터를 B의 다음 요청이 분석하던 문제. 이 경로만 그리로 되돌아가 있었고, Agent Mode가 어디에서도 실행된 적이 없어 아무도 몰랐다.

`contextvars.copy_context()`로 고쳤다. 고치기 전 7단계·설명 실패 → 고친 뒤 **10단계 전부 완료**(설명·검증·보고서·API 준비도까지).

`scripts/run_agent_mode_smoke.py`가 이 경로를 지킨다. **보는 것은 "200이 왔다"가 아니라 "사슬이 끝까지 갔다"이다** — 200은 그때도 계속 오고 있었다. 수정 전 서버에 대고 돌리면 3건이 실패한다.

### 프런트엔드가 부르는 엔드포인트가 백엔드에 있는가

두 계층이 한 계약을 공유하는데 **맞춰보는 곳이 없었다.** 백엔드 라우트 이름을 바꾸면 프런트엔드는 조용히 깨진다 — pytest는 백엔드만 보고, 제품 스모크는 HTTP API를 직접 치며(프런트가 쓰지 않는 경로도 포함해서), `vite build`는 문자열 안의 URL을 검사하지 않는다. **사용자만 안다.**

이 저장소들이 반복해서 찾아온 모양이다: 같은 질문에 답하는 장치가 둘인데 어긋나는지 보는 것이 없다. 누출 검사기와 평가 관문이 그랬고, export 검증기와 원장이 그랬고, `can_rerun`과 재실행 엔드포인트가 그랬다.

**호출 99개가 전부 실재하는 라우트를 가리킨다** — 빈손이다. 그래도 다음에 라우트 이름이 바뀌면 여기서 걸린다.

### 목록이 남의 것을 보여주지 않는가

프런트가 부르는데 CI가 한 줄도 실행하지 않던 스물넷 중 **목록 읽기 네 개**를 쳤다 — 프로젝트, 실험 기록, 리포트, 학습 작업. 넷 다 `WHERE user_id=?`로 자기 것만 고른다고 쓰여 있었고, **그 조건이 실제로 거는지는 확인된 적이 없었다.**

이 저장소가 이미 겪은 실패의 반대편이다. 요청 격리를 고치기 전에는 A가 올린 데이터셋을 B의 다음 요청이 분석했다 — `STATE` 하나를 프로세스가 공유했기 때문이다. 그건 고쳤고, **DB 쪽 범위는 각 질의의 `WHERE`에 달려 있다.** 조건 하나가 빠지면 목록 하나가 남의 작업 제목을 보여준다.

거부만 확인하면 전부 빈 목록을 주는 구현도 통과한다. 그래서 **본인은 보이고 남은 안 보이는** 것을 한 검사 안에서 함께 본다. 기록만 관리자에게 전체를 보여주는데, 그 예외도 함께 고정했다 — 조용히 사라지면 관리자가 못 보고, 조용히 넓어지면 모두가 다 본다.

세 곳의 `WHERE`를 각각 빼서 셋 다 잡히는 것을 확인했다.

**전체 스위트에서만 실패하는 검사를 하나 만들었다.** `STATE`가 비었다고 가정했는데, 앞선 테스트가 학습을 돌려 기본 버킷에 모델을 남기면 "모델이 없을 때"를 시험한다던 검사가 모델이 있는 상태를 본다. **전역 상태에 기대는 검사는 그 상태를 스스로 세워야 한다** — 요청 격리를 만들며 붙인 `set_scope`로 이 테스트만의 빈 버킷을 연다. 제품 코드가 요청마다 하는 일을 검사도 한다.

**두 번 짐작이 틀렸다.** `explain_summary`가 빈 근거를 돌려줄 것이라 적었는데 400으로 거부한다. 그리고 `validation_summary` 검사의 첫 단언이 `... or summary`로 끝나 **무엇이 오든 통과**하는 상태였다 — 대조를 걸기 전에 눈에 띄었다. 참인 것을 확인하는 단언과 아무것도 확인하지 않는 단언은 통과 화면에서 똑같아 보인다.

### 라우트 백 개마다 부르는 쪽이 있는가

"CI가 실행하지 않는다"와 "아무도 부르지 않는다"는 다른 질문이다. 앞은 검사의 빈 곳이고 뒤는 **표면의 빈 곳**이다. 근거 셋으로 물었다 — 프런트엔드의 `api.<메서드>` 호출, 스모크 열다섯, 문서.

**여섯이 남았다.** 넷은 legacy `STATE` 흐름의 옛 API 쌍둥이다(`/api/predictions`, `/api/shap-local/{idx}`, `/api/columns`, `/api/llm/status`) — 프런트는 같은 기능을 다른 경로로 부른다. 하나는 `/api/admin/users`로, **검사는 있는데 부르는 화면이 없다**(관리자 UI는 요약·피드백·문의·모니터링 넷만 부른다). 마지막은 SPA 캐치올이고, 브라우저가 주소창으로 치는 자리라 호출이 있을 수 없다.

**지우지 않았다.** `docs/legacy-analysis-flow-audit.md`가 이 흐름의 기능들을 "Preserved"로 분류하고 *"동등한 빠른 분석 경로가 남지 않는 한 대체하지 말 것"*이라고 적어뒀다. 내부 스캔만으로 공개 표면을 지우는 것은 그 결정을 내 판단으로 덮는 일이고, 베타로 배포된 적이 있어 바깥 호출자가 없다고 단정할 근거도 없다. **대신 이름으로 뒀다** — 하한선으로는 하나가 늘어나는 것을 못 본다.

**찾는 동안 매처가 두 번 틀렸다.** 처음엔 `{model_id}`를 지워 `/api/v2//predict`를 찾았고, 다음엔 프런트가 axios `baseURL` 때문에 `/api` 없이 부른다는 것을 놓쳤다. **둘 다 "언급 없음"을 결과처럼 보이게 했다** — 16개라고 두 번 잘못 세고, 아는 답 다섯 개를 대조로 박고서야 여섯이 나왔다. 그 다섯은 검사에 남겼다.

**그리고 이 절을 쓰자마자 검사가 빨개졌다.** 문서가 근거 중 하나인데, "이 넷은 아무도 부르지 않는다"고 **적는 행위가 그 넷을 언급으로 만든다.** 다섯이 곧바로 "이제 누가 부름"으로 뒤집혔다 — 인용과 사용을 혼동한 것이 이 저장소들에서 아홉 번째다. 이 절을 `<!-- surface-record: -->` 울타리로 감싸고 검사가 그 안을 걷어내게 했다. 울타리 밖의 언급은 여전히 근거로 세고, 울타리를 없애면 실패한다.

### 인증 없이 쓰는 경로 셋, 그리고 내 대조가 두 번 헛돌았다

CI가 한 줄도 실행하지 않는 라우트 마흔 개 중 **스물넷은 프런트가 부르는데 아무 검사도 치지 않는다.** 그중 셋이 **인증 없이 쓰는 경로**다 — 파일럿 문의, 베타 피드백, 프런트엔드 오류 보고. 로그인 없이 도달하고 셋 다 DB에 행을 쓴다.

셋 다 입력을 다듬는 코드를 갖고 있다. 그 코드가 한 번도 돌아본 적이 없었다. 스물일곱 개를 넣었다.

**그리고 대조를 걸었더니 둘이 안 물렸다 — 내 테스트가 엉뚱한 겹을 시험하고 있었다.**

**차단 목록은 도달할 수 없다.** `{"password": ...}`가 버려지는 것을 보고 차단 목록이 일한다고 읽었는데, `password`는 **허용 목록에도 없어서 첫 겹에서 이미 걸린다.** 차단 목록을 통째로 꺼도 검사는 통과했다. 허용 목록 열 개 중 차단 낱말을 품은 이름이 하나도 없으므로 안쪽은 영영 조용하다. 지우지 않고, **그 전제가 바뀌면 말하도록** 바꿨다.

**길이 자르기도 마찬가지였다.** 핸들러의 `[:500]`을 지워도 통과한다 — 실제로 자르는 것은 `persist_monitoring_event`다. 저장된 값만 보면 어느 겹이 잘랐는지 알 수 없다. **보장은 제공하는 층에서 시험해야 한다.**

**세 번째로, 고친 검사조차 헛돌았다.** 허용 목록을 테스트에 옮겨 적었더니 소스에 낱말을 추가해도 조용했다 — **사본은 소스가 바뀌어도 그대로다.** 짝인 두 목록 중 차단 쪽만 모듈 상수였고 허용 쪽은 함수 안 지역 변수여서 읽을 수가 없었다. 같은 자리로 올리고 검사가 소스를 읽게 했다.

### 의존성을 고정했다 — 버전은 손으로 적지 않았다

`requirements.txt`가 열여섯 개를 **이름으로만** 적고 있었다. 갓 설치하면 그날 최신이 잡히고, 이 저장소가 공개하는 숫자는 어느 한 조합 위에서 나온 것인데 **어느 조합인지 아무 데도 없었다.** 핸드오프 문서 §6.3이 위험으로 적어뒀고 두 달 그대로였다.

**막힌 지점이 있었다.** 개발 기계에 `shap`과 `optuna`가 설치돼 있지 않아 열여섯 중 둘의 버전을 읽을 수 없다. 짐작으로 적으면 **확인된 것처럼 보이는 추측**이 되고, 그건 고정하지 않은 것보다 나쁘다 — 읽는 사람이 검증된 값이라고 믿는다.

그래서 CI에 `pip freeze` 단계를 넣고 **갓 설치가 실제로 무엇을 잡는지 찍어서** 그 값을 옮겼다(Python 3.11.16). 개발 기계와 달랐다:

    fastapi   0.140.7  →  0.141.1
    numpy     2.1.2    →  2.4.6
    openai    2.49.0   →  3.3.1

**한쪽에서 통과한 숫자가 다른 쪽에서 같으리라는 보장이 없다**는 것이 고정하는 이유다.

**전이 의존은 고정하지 않았다.** 전체 잠금은 한 파이썬에서 푼 것이 다른 파이썬에서 풀린다는 보장이 없고, 이 저장소의 CI는 3.11(`tests`)과 3.12(`product`) 둘 다 쓴다. **확인한 범위까지만 고정한다** — 그 범위를 넘어 적으면 다시 추측이다. `pip freeze` 단계는 관문이 아니라 **다음에 핀을 갱신할 근거**로 남겼고, 검사가 그 단계가 사라지는 것도 막는다.

### SHAP이 아닌 것을 SHAP이라 부르지 않는다 — 도구 카탈로그에서도

의존성을 고정하려고 설치된 버전을 읽다가 **`shap`과 `optuna`가 이 개발 환경에 없다**는 것을 봤다. `SHAP_OK=False`인데 스위트도 스모크도 초록이었다. 그 사슬을 따라갔다.

`backend/tools/shap_explainer.py`에는 **`import shap`이 한 줄도 없다.** feature importance나 표준화 계수를 돌려주고, 페이로드의 `explanation_type`은 그것을 정직하게 말한다. 파일 자신이 주석으로 적어뒀다 — *"Never claim SHAP for something that is not SHAP."*

**그 규칙이 두 곳에 닿지 않았다.**

첫째, 도구 카탈로그. `registry.py`가 이 도구를 *"Returns SHAP, feature importance, coefficient, or unavailable evidence"*라고 소개했다. 그 문장은 `mock_response.summary`에 있고 `describe()`가 그대로 내보내므로 도구 목록을 읽는 쪽이 그대로 본다. **나올 수 없는 것을 나올 수 있다고 적어둔 것**이고, 그 한 단어가 설명에 실릴 무게를 정한다.

둘째, 스모크. `run_agent_mode_smoke.py`가 "설명 단계가 돌았다"를 **단계 이름**으로 판정했다 — `tool_name == "shap_explainer_tool"`. 이름이 곧 주장인 상황에서 이름은 판정 근거가 될 수 없다. 이제 `explanation_type`까지 보고, 출력이 **실제로 무엇이었는지**를 말한다.

이름 자체는 그대로 뒀다. 저장된 실행 기록이 그 이름을 참조하고, 바꾸면 지난 기록이 가리키는 도구가 사라진다. **바꾼 것은 이름이 아니라 이름이 하는 약속**이다.

README는 이미 이 규칙을 적어두고 한 번 적용했다(계수를 `standardized_coefficient`로 개명). **같은 규칙의 두 번째 위반이 같은 저장소 안에 남아 있었다.**

### 문서가 두 번 적어둔 보안 항목이 두 달간 그대로 있었다

지난 회차의 측정에서 **CI가 한 줄도 실행하지 않는 라우트 마흔 개**가 나왔다. 그중 프런트엔드가 부르지 않는 열여섯을 추렸다 — "아무도 부르지 않고 아무도 시험하지 않는 경로". 그 목록에 `GET /api/debug-env`가 있었다.

    @app.get("/api/debug-env")
    async def debug_env():
        key = os.getenv("GEMINI_API_KEY", "")
        all_keys = sorted(os.environ.keys())
        gemini_keys = [k for k in all_keys if "GEMINI" in k.upper() or "API" in k.upper()]

인증이 없고, 환경 변수 이름 중 "GEMINI"나 "API"가 든 것을 모으고, **반환하지 않는다.** 오늘은 `null`을 주지만 누가 한 줄만 되돌리면 인증 없는 경로가 키 이름 목록을 뱉는다.

**`docs/MODEL_MATE_HANDOFF.md`가 §6.2와 §8.1 두 곳에서 "제거하거나 보호하라"고 적어뒀고**, 2026-06-22 감사 스냅숏도 같은 말을 했다. 두 달 동안 그대로였다. **손으로 적어둔 조치는 확인하는 검사가 없으면 조치가 아니다** — 이 저장소들이 도구와 스모크에서 이미 두 번 적은 문장이고, 세 번째가 문서의 조치 목록이었다.

지웠다. 프런트가 부르지 않고(호출 99개를 훑었다), 스모크 열다섯 중 어느 것도 치지 않으며, 반환값이 없으니 잃는 동작이 없다. `tests/test_no_environment_disclosure.py`가 경로·핸들러 이름·`os.environ` 통째 읽기를 막고, **문서가 다시 "위험"이라고 말하면 실패한다.**

**같은 문서의 나머지 항목도 실측했다.** 기본 JWT·관리자 비밀번호(해결), 추적되던 런타임 산출물(해결), 고정되지 않은 의존성(**16개 중 0개 고정 — 그대로 열려 있다**). 해결된 것은 검사로 묶었다.

그 과정에서 **내가 쓴 문장 하나를 정정했다.** "설정 없이 부팅하면 죽는다"고 적었는데 실제로는 **배포로 판단될 때만** 그렇고 로컬에서는 난수를 만들어 저장한다. 그리고 그 검사를 쓰다가 **여덟 번째로 인용/사용 함정에 걸렸다** — 옛 기본값을 설명하는 독스트링이 옛 기본값을 쓰는 코드로 읽혔다.

### 잴 수 없다던 것을 쟀다 — 그리고 CI가 지키던 것은 47%였다

형제 저장소 넷은 분기 커버리지 100% 관문을 얻었는데 여기만 **잴 방법이 없다**고 로드맵에 적혀 있었다. `main.py`가 `main_parts/*.part`를 이어붙여 `exec`하면서 넘기는 파일명이 디렉터리라, coverage.py가 그 이름을 파일로 열지 못한다.

잴 방법은 있었다. 이어붙인 소스는 유효한 파이썬이고 줄 번호는 되돌릴 수 있다 — 파일 사이에 `join`이 한 줄을 넣으므로 그 한 줄만 더하면 정확히 맞는다. `scripts/measure_part_coverage.py`가 `sys.settrace`로 우리 프레임만 따라간다. **관문이 아니라 어디를 봐야 하는지 알려주는 물건**이다(스위트가 두 배쯤 걸린다).

    .part 소스 4,256문 기준
    pytest만                          27.7%
    CI가 돌리던 스모크 셋               44.5%
    **둘을 합쳐 CI가 지키던 것**        47.3%
    스모크 열다섯을 다 돌렸을 때         56.8%

**세 가지가 나왔다.**

**첫째, pytest가 스모크에 더하는 것은 92문뿐이다.** 743개 테스트가 앱 자체에 대해서는 스모크가 이미 지나간 곳을 거의 그대로 지나간다. pytest는 헬퍼와 관문 로직을 촘촘히 보고, 라우트 사슬은 스모크가 본다 — 그 분업 자체는 합리적이지만, **"테스트 743개"가 앱의 절반을 지킨다는 뜻은 아니다.**

**둘째, 스모크 열다섯 중 CI가 돌리던 것은 셋이었다.** 나머지 열둘은 저장소에 들어 있고 손으로 돌리는 것이었다. 이 저장소들은 *"손으로 돌리는 검사는 돌리지 않으면 없는 검사다"*를 이미 두 번 적어뒀다. 열둘이 **9.4%p**를 더 짚으므로 CI에 넣었다 — 서버는 이미 떠 있으니 값은 실행 시간뿐이다. 그중 둘은 관리자 로그인이 필요해서, 부팅 때 이 실행 한 번짜리 비밀번호를 건다.

**셋째, CI 기준으로 한 줄도 안 도는 함수가 132개**다(전체 321개 중). `run_optuna`, `run_agent`, `predict_single`, `run_shap`, `auth_google` 같은 **살아 있는 라우트 핸들러**가 그 안에 있다. 죽은 코드인지 먼저 확인했고 — 전부 `@app.post`로 물려 있다 — 그래서 죽은 코드가 아니라 **시험되지 않는 기능**이다. 목록은 로드맵에 남겼다.

**보고 단위도 한 번 틀렸다.** 처음엔 `.part` 파일별로 냈고 "이 파일은 0%"가 셋 나왔다. 들여다보니 앞 파일에서 시작한 함수의 **꼬리**였다 — `.part` 경계는 기능 경계가 아니다. 함수 단위로 다시 묶은 것이 위 숫자다.

### 소유권 문지기 넷이 남의 것을 막는지 확인한 적이 없었다

위 계측의 다음 조각이다. `_resource_not_found()`는 네 문지기가 공유한다 — 프로젝트·데이터셋·분석 실행·배포 모델. 그 넷이 **남의 자원을 막는지 한 번도 발동된 적이 없었다.**

**404를 쓰는 것은 의도된 선택이다.** 남의 프로젝트에 403을 주면 "그 id는 존재한다"를 알려주는 셈이고, 그것은 이 저장소가 로그인에서 이미 막은 종류의 누출이다(계정 존재 여부를 응답 시간으로도 알 수 없게 만들었다). 그래서 검사는 거부만 보지 않고 **없는 자원과 남의 자원이 같은 답을 내는지** — 상태 코드와 문구를 둘 다 — 비교한다. 소유자와 관리자가 통과하는 것도 함께 고정한다. 전부 거부하는 구현이면 거부 검사만으로는 아무것도 증명되지 않는다.

게스트 경로 둘(소유자 없는 옛 실행, 공개 모델 메타데이터)은 **열려 있다는 사실**도 고정했다. 조용히 닫히면 옛 실행이 안 열리고, 조용히 넓어지면 남의 자원이 열린다.

**CI가 잡은 것이 하나 더 있다.** `analysis_runs`는 **게으르게 만들어진다** — 에이전트 경로가 처음 쓸 때 `CREATE TABLE IF NOT EXISTS`로 만든다. 갓 설치한 곳에는 없고 CI가 정확히 그 상태다. 내 픽스처는 그 표가 있다고 가정했고, 문지기는 이미 알고 있었다(`sqlite3.OperationalError`를 잡아 "없는 자원"으로 다룬다). **그 갈래도 한 번도 발동된 적이 없었다** — 잡지 않으면 갓 설치한 서버에서 어떤 실행을 조회하든 500이 나고, **500은 "당신 것이 아니다"가 아니라 "우리가 고장났다"이다.** 임시 DB를 가리켜 그 상태를 만들어 확인한다.

**이 파일을 쓰다가 내가 테스트 두 개에 같은 이름을 붙였다.** 파이썬은 뒤엣것을 남기고 앞엣것을 버리며 pytest는 아무 말도 하지 않는다 — 수집 개수가 하나 줄 뿐이고, 새 테스트가 함께 들어오면 그 감소는 상쇄돼 보이지 않는다. 다섯 저장소를 훑는 검사를 프로필 저장소의 도구에 넣었고, 다른 곳에는 없었다.

### HTTP 거부 101곳 중 스위트가 발동시키는 것은 3곳이었다

스위트가 도는 동안 `HTTPException`이 **실제로 발생한 자리**를 기록했다. `.part` 파일들은 이어붙여 `exec`되므로 프레임의 파일명이 디렉터리 경로다 — 줄 번호는 이어붙인 소스 기준이라 되돌릴 수 있고, 그렇게 매핑했다.

    소스의 HTTPException 발생 지점        101곳
    스위트가 실제로 발생시킨 지점            3곳

세 곳은 한도 초과(429) 둘과 타깃 설정 실패(400) 하나다. **계측기를 먼저 의심했다** — parts 밖에서 난 예외를 놓치는 것 아닌가 싶어 그것까지 기록하도록 넓혀 다시 돌렸다. 여전히 3곳이었고, 기록된 세 줄에 실제로 `HTTPException(`이 있는 것도 확인했다.

**권한 거부 열여섯이 그 안에 있었다** — 관리자 전용 403이 아홉, 로그인 필요 401이 셋, 내려간 예측 API 410이 둘. 관리자 엔드포인트를 먼저 고른 이유는 분명하다: **조건 하나가 뒤집혀도 정상 사용자는 아무 차이를 못 느낀다.** 관리자만 쓰는 화면이고, 뚫린 것은 뚫린 뒤에야 보인다.

비관리자와 익명 호출자로 아홉 개를 각각 쳐서 403을 확인하고, 401 셋도 같이 넣었다. 검사가 공허하지 않은지도 함께 본다 — 관리자 판정이 참을 낼 수 있는가, 목록이 소스의 403 개수와 같은가. 관리자 검사를 지우면 실패하는 것을 세 곳에서 확인했다.

**메서드까지 함께 본다.** 경로는 있는데 그 메서드가 없는 경우가 실제 실패 모드이고, 경로만 비교하면 `DELETE /api/state`가 통과한다. 없는 경로와 없는 메서드 둘 다로 잡히는 것을 확인했다.

### 서빙되는 프런트엔드가 현재 소스에서 나온 것인가

백엔드가 `frontend/dist`를 정적으로 서빙하고 그 dist는 저장소에 커밋돼 있다 — 배포에 빌드 단계가 없다. 그런데 **아무것도 dist와 src를 묶어두지 않았다.** `src`만 고치고 빌드를 잊으면 앱은 옛 코드를 서빙하는데 **모든 검사가 통과한다**: 제품 스모크는 HTTP API를 치고, `vite build`는 성공하고, pytest는 백엔드만 본다. 사용자만 안다.

빌드 결과를 다시 만들어 비교하지 **않는다.** 그건 툴체인이 바이트 단위로 재현될 때만 성립하고, node·vite 버전이 조금만 달라도 거짓 실패를 낸다 — **거짓 실패를 내는 검사는 사람들이 끄는 검사다.** 대신 빌드 **입력의 지문**을 dist 옆에 남기고 그걸 비교한다.

(2026-08-21 기준 `npx vite build`는 커밋된 dist를 바이트 단위로 재현한다. 그래도 지문을 쓰는 이유는 위와 같다 — **오늘 재현된다는 것과 다른 기계에서도 재현된다는 것은 다른 주장이다.**)

`src`를 한 줄 고쳐 잡히는 것, 자산이 사라져도 잡는 것, 지문이 없으면 통과가 아니라 실패하는 것을 확인했다.

로컬 실행은 아래 **Local Setup** 참조. 저장소는 `github.com/ohsewool/modelmate`이며, 예전 주소 `ohsewool/-`는 이름을 바꾼 것이라 리다이렉트된다.

### 요청 격리

업로드된 데이터프레임·학습된 모델·SHAP 값은 `STATE`에 산다. 그것이 **프로세스 전체가 공유하는 딕셔너리 하나**였다. 로그인이 붙은 배포 환경에서 그 뜻은, A가 올린 데이터셋을 B의 다음 요청이 분석한다는 것이다 — B가 자기 데이터를 함께 보내지 않는 한.

직전 업로드를 재사용하는 것 자체는 의도된 동작이다(데이터셋이 없을 때의 오류 메시지도 "기존 업로드된 데이터셋을 쓰라"고 안내한다). 결함은 재사용이 아니라 **"기존"의 범위**였다.

`backend/scoped_state.py`가 `STATE`를 같은 매핑 인터페이스로 유지하면서 어느 버킷을 가리킬지를 요청별 컨텍스트 변수로 정한다. **`.part` 파일 35곳의 STATE 사용 266건은 한 줄도 바뀌지 않았다.** 범위 키를 266곳에 꿰는 것은 배포된 앱에 가할 변경으로 너무 크고, 그 대부분은 스코핑을 알 이유가 없는 세 줄짜리 핸들러다.

두 가지가 성립해야 했고 성립한다.

- **범위를 설정하지 않으면 이전과 똑같이 동작한다.** 스크립트·테스트·신원 없는 경로는 공용 기본 버킷을 쓴다. 이 변경이 설치되는 것만으로 무언가를 깨뜨릴 수 없다.
- **클라이언트는 남의 범위에 닿을 수 없다.** 원래 여기 적혀 있던 문장은 "범위는 호출자가 고르지 않는다"였고, **절반이 틀렸다.** 계정 범위는 서명된 토큰의 `sub`라 서버가 정하지만, 데모 게스트 범위는 클라이언트가 보낸 `x-modelmate-guest-session` 헤더에서 나온다 — 클라이언트가 문자열을 고른다.
  실제로 성립하는 것은 더 좁다. 서버가 `guest:` 접두사를 붙이고 헤더에서 콜론을 지우므로 `guest:<무엇이든>`이 계정 식별자(UUID)와 같아질 수 없고, 공유 기본 버킷에도 닿을 수 없다. 계정 id 그대로·`../`·접두사 흉내·널 바이트·`__default__`를 전부 시도해도 `guest:` 아래로 떨어진다.
  **성립하지 않는 것도 적어둔다**: 같은 세션 id를 보낸 두 게스트는 버킷을 공유하고, 정제 때문에 `a:b:c`와 `abc`가 같은 범위가 된다. 세션 식별자의 본성이고 쿠키와 다르지 않다 — 감추면 같은 과신을 작은 글씨로 반복하는 것이다. `tests/test_scope_is_not_client_choosable.py`가 양쪽을 다 고정한다.
  (docstring은 지난 회차에 고쳤는데 **이 문장을 못 고쳤다.** 같은 주장이 두 곳에 살면 한 곳만 고쳐진다 — 이 프로젝트가 반복해서 만나는 모양이고, 이번엔 내가 만들었다.)

### 사람 검토 관문이 거부 목록으로 만들어져 있었다

검토 큐도 테스트가 0개였고, **잃는 방향이 같은 결함이 둘** 있었다.

`should_create_review_item`이 "검토가 필요한 판단" 집합을 **거부 목록**으로 썼다. 목록에 없는 판단은 검토가 생기지 않는다 — executor가 실제로 내보내는 `block_execution`이 그냥 지나갔고, `abort_and_delete_dataset` 같은 것도 마찬가지였다.

**진행하면 안 되는 것을 잡는 큐를 "진행하면 안 되는 것 목록"으로 만들 수는 없다.** 위험한 경우는 언제나 아무도 목록에 넣을 생각을 못 한 그것이기 때문이다. 허용 목록으로 뒤집었다 — 모르는 판단은 사람이 본다. 이 방향으로 틀리면 검토자가 평범한 항목 하나를 더 보고, 반대 방향으로 틀리면 파괴적 동작이 아무도 못 본 채 지나간다.

`review_id`는 실행+단계+사유였다. 그래서 **같은 단계의 서로 다른 문제 둘이 같은 id를 가졌다** — `critical` 관측과 `error` 관측이 같은 식별자를 받았고, id로 저장하는 쪽은 하나를 잃는다. 내용 지문을 붙여 분리하되, 같은 판단을 재처리하면 같은 id가 나오게 유지했다(재시도가 큐를 복제본으로 채우지 않도록).

### 감사 기록이 없는 근거를 가리킬 수 있었다

에이전트가 무엇을 보고 왜 그렇게 했는지는 `persistence.py`(996줄)에 남는다. **테스트가 하나도 없었다.**

모든 테이블이 `FOREIGN KEY`를 선언한다. **SQLite는 `PRAGMA foreign_keys`가 켜져야 그걸 지키고, 기본값은 꺼짐이다.** 즉 결정이 존재한 적 없는 관측을 인용할 수 있었고, 만들어진 적 없는 실행에 매달릴 수도 있었다. 둘 다 실증한 뒤 고쳤다.

일반 데이터베이스보다 여기서 더 나쁘다. 이 행들은 자동화된 판단의 **근거**이고, 참조가 아무 데도 닿지 않는 근거는 근거가 아니다. 제약은 적혀 있었고 켜는 것만 빠져 있었다 — 정의만 되고 배선 안 된 통제와 같은 형태다.

### 설명이 모델보다 틀렸던 곳

설명 도구에는 테스트가 하나도 없었다. `feature_importances_`가 없는 모델(로지스틱 회귀 등)에서는 **계수 크기를 그대로 중요도 순위로** 썼는데, 계수는 "이 컬럼 1단위당 효과"이고 단위는 컬럼끼리 비교되지 않는다. 그렇게 매긴 순위는 중요도가 아니라 **측정 단위**를 매긴다.

데모 데이터는 `scripts/make_demo_data.py`가 생성하므로 참값이 있다. 모델이 학습한 계수는 생성에 쓴 값과 소수점 둘째 자리까지 일치했다 — **모델은 옳았고 설명이 틀렸다.**

| | 옛 순위 (계수) | 참 영향력 (계수 × σ) |
|---|---|---|
| 1위 | support_tickets | **tenure_months** |
| 2위 | contract_type | last_login_days |
| 3위 | **tenure_months** | support_tickets |

`support_tickets`는 0~6, `tenure_months`는 1~71을 오간다. 단위당 계수는 전자가 크지만 관측 범위 전체의 영향력은 후자가 약 3배다. 표준편차로 정규화해 고쳤고, 이름도 `standardized_coefficient`로 바꿨다 — **SHAP이 아닌 것을 SHAP이라 부르지 않는다.**

고치는 과정에서 하나 더 있었다. 처음에 `backend/tools/shap_explainer.py`를 고쳤는데 **그 경로는 돌지 않는다** — `backend.main`에 `global_explanation_items`가 있으면 그쪽이 먼저 반환한다. 진짜 로직은 `main_parts/032`에 있었다.

### 권고를 따라도 결과가 같았다

한 층 위에 같은 모순이 하나 더 있었다. 관문들이 읽는 `leakage_risk`는 **데이터셋 전체**에 대한 판정인데, 관문은 그것을 **학습된 모델**에 대한 것으로 읽었다.

그래서 표시된 컬럼을 전부 제외한 사용자도 `invalid` / `blocked`에 도달했다 — **무시한 경우와 완전히 같은 판정이다.** 결과를 바꿀 수 없는 권고는 권고가 아니다.

학습이 끝난 뒤 **실제로 사용된 특징**만으로 다시 검사한다. 그것이 관문이 실제로 묻는 질문이다 — *이 모델이 누출 위에 서 있는가.* 데모 데이터에서 제외 전 `high`, 제외 후 `low`이고, 그 차이가 이 체인 전체가 만들어내려던 것이다.

| 시나리오 | 누출 | 증거검증 | 배포 |
|---|---|---|---|
| 누출 방치 | high | invalid | **blocked** |
| 권고 적용 | low | grounded | needs_review |
| 깨끗한 데이터 | low | grounded | needs_review |

재검사가 실패하면 필드를 비워 둔다 — 그러면 관문이 데이터셋 전체 판정으로 되돌아가고, 그게 안전한 방향이다. **실패가 "누출 없음"으로 읽히면 안 된다.**

### 두 안전장치가 서로 반대로 말하고 있었다

누출 검사기는 타깃을 재현하는 컬럼을 빼라고 한다. 데모 데이터에서 그러면 AUC가 1.000에서 0.778로 내려가고, **평가 관문의 통과선(0.80)을 넘지 못한다.**

즉 **권고를 따르면 무시했을 때보다 나쁜 판정을 받았다.** 나쁜 모델을 잡으라고 있는 관문이 누출에 상을 주고 있었다.

고치는 방법은 통과선을 낮추는 게 아니다 — 그건 근거 없는 숫자를 다른 근거 없는 숫자로 바꾸는 것이다. **지표는 그것이 얻어진 특징만큼만 의미가 있다.** 높은 누수 위험 위에 앉은 높은 점수는 모델에 유리한 증거가 아니라 불리한 증거다. 그래서 "의심스럽게 높음" 임계값을 새로 만드는 대신, **누출 검사기가 이미 계산한 심각도를 읽는다.**

기본 통과선 0.80/0.65는 표준이 아니라 출발점이라고 명시했다. 0.75 ROC-AUC는 값어치 있는 이탈 예측 모델일 수도, 쓸 수 없는 임상 모델일 수도 있고 이 파일은 어느 쪽인지 모른다. **이 프로젝트의 데모가 통과하도록 0.75로 낮추지 않았다** — 그건 표본에 기준을 맞추는 일이다.

### 누출 검사가 실제로 모델을 바꾼다

```bash
python3 -m pytest tests/ -q          # 1058 tests
```

게이트를 하나씩 검증하는 것과 그 권고가 모델에 도달하는지는 다른 문제다. 무시되는 권고는 안전이 아니라 서류다. 같은 데이터를 두 번 학습해 실측했다.

| | ROC-AUC |
|---|---:|
| 누출을 둔 채 학습 | **1.0** — 교과서적 누출 신호 |
| 검사기 권고 적용 | **0.778** — 깨끗한 데이터와 일치 |

이 격차가 제품이 작동한다는 증거다.

검사는 이름이 아니라 **컬럼이 무엇을 하는지**를 잰다. 이름만 보던 시절에는 `exit_survey_score`가 잡혔지만 이유가 "score"라는 단어였고, `wellbeing_index`로 이름만 바꾸면 같은 값·같은 분리력(8.43 대 2.08)으로 그냥 통과했다. 경위는 [`docs/DEMO_DATA.md`](docs/DEMO_DATA.md).
